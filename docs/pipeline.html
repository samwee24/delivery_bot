How the robot works

Two sensors, one join, one decision, one actuator, and a loop that closes through the room rather than through code.

Tap a box to jump to that part of the walkthrough, or scroll and open the stages yourself.

Where you come in

Four ways to touch the robot. The first three are commands you type; the fourth is the Foxglove session on a laptop. Nothing else takes input — there is no button on the robot.

Run a delivery
ros2 run delivery_bot_mission deliver -- seat_1 seat_2

Sends one Nav2 goal per name, then home. Ctrl+C cancels the current task and leaves the watchdog to stop the wheels.

Teach a goal
ros2 run delivery_bot_mission save_goal seat_2

Put the robot where the seat is, run this, and its current map-frame pose is written into goals.yaml in the source tree, so the change can be committed. Positions are recorded, never typed.

Drive it yourself
ros2 run teleop_twist_keyboard teleop_twist_keyboard -p stamped:=true

Keys go straight to /cmd_vel. This bypasses Nav2 entirely — no planner, no costmap, no obstacle stopping.

Watch, or click a goal
ws://192.168.31.109:8765

Foxglove shows /scan, TF, costmaps and filtered odometry. Its Nav2 panel can also publish a goal, which is the same path as deliver.

teleop and Nav2 both write /cmd_vel and nothing arbitrates between them — if both are live, the faster publisher wins. Stop means Ctrl+C, or letting the 0.5 s watchdog expire.

Start to finish

00Power on, build, sourceonce per session

The Pi boots, swap mounts, and the workspace is sourced. colcon build --symlink-install compiles the four packages we own; rf2o is cloned from deps.repos and pinned at b38c68e, so a rebuild is reproducible instead of "whatever was on the SD card".

deps.repos.github/workflows/ci.yml/swapfile

a parallel build without swap takes the machine off SSH — it happened; build one job at a time.

01Launch the graphbase.launch.py

Seven nodes start at once: robot_state_publisher (URDF → tf_static), the lidar driver, rf2o, imu_node, the EKF, motor_node and foxglove_bridge. The launch file forces dry_run: true, so the motors compute and log duty cycles without touching a pin.

bringup/launch/base.launch.pyurdf.xacro:8765

a missing /dev/rplidar kills the driver and the whole graph loses /scan; a stale bridge left on 8765 blocks the new one.

02Lidar: one revolution, one scan5–7 Hz

The A1M8 spins and streams range packets at 115200 baud; the driver assembles them into a LaserScan on /scan with frame_id: laser. Each revolution asks about 284 times, and on this unit only 95–105 answers come back.

lidar.launch.pyscan_mode: Standard/scan

roughly a third of the ring is empty before any code runs — a photonic or mounting cause, and every stage below inherits it.

03IMU: yaw rate only100 Hz

MPU6050 over I²C at 0x68, three seconds of still-bias calibration, then gyro z in rad/s on /imu/data. There is no magnetometer, so absolute heading is impossible: the node sets orientation_covariance[0] = -1 to tell every consumer that field is invalid.

drivers.yamlcalib_max_std 0.01/imu/data

i2cdetect -y 1 is currently empty — no 0x68 on the bus, so this stage has provably never produced a sample.

04Lidar odometry: range flow10 Hz

rf2o compares consecutive scans and solves for the motion that best explains the change in ranges. It publishes velocity — vx and vyaw — not a pose, which is why a drift-prone position is never trusted downstream.

/scan → /odom_rf2opublish_tf: falsebase_frame_id: base_footprint

with a third of the ranges missing, the flow field is thin in exactly the sectors where the room is open, so the estimate is noisiest where it matters.

05Fusion: one owner of the odometry frame30 Hz

robot_localization in 2D mode predicts at 30 Hz and corrects with rf2o's vx/vyaw plus the IMU's vyaw. It is the only publisher of odom → base_footprint. No accelerometer, no absolute position: x and y are integrals, so drift is bounded only by the quality of the velocity estimates.

ekf.yamltwo_d_modeworld_frame: odom

a second publisher of that transform makes the map rotate on the spot, which looks exactly like broken hardware.

06Map, or remember the mapper scan

slam_toolbox matches each scan against what it already knows and publishes map → odom plus /map. In mapping mode it grows a new map, saved as maps/room.yaml plus a serialised pose graph.

slam_mapping.yamlslam_localization.yamlmaps/

sparse scans produce walls that wobble; an unclosed loop makes the map jump when the robot comes home.

07Decide where to goon goal

A goal arrives in the map frame from goals.yaml via deliver. Nav2's planner finds a path over the costmap and the controller follows it at 0.15 m/s, publishing /cmd_vel as TwistStamped.

nav2_params.yamlgoals.yaml/cmd_vel

an unstamped Twist is silently ignored — the robot looks dead while every topic appears healthy.

08Turn velocity into volts20 Hz

motor_node splits velocity into left and right wheel speeds, applies a dead zone and a gain per side, clamps at max_duty 0.85, and drives the L298N on GPIO 12/5/6/13/20/21. If no command arrives for 0.5 s it zeroes PWM and pulls the direction pins low.

drivers.yamldry_runwatchdog_s 0.5

teleop and Nav2 both publish /cmd_vel with no arbiter — there is no safety node yet, so the watchdog is the only protection.

09Observe, record, close the loopcontinuous

Foxglove on 8765 shows scans, TF, costmaps and filtered odometry; ros2 bag -s mcap records the topics that matter; one row goes into test_log.md per run with a commit hash and a number. And the loop closes: a wheel turn changes the next scan, which changes the next velocity estimate.

foxglove_bridgeros2 bagdocs/test_log.md

nothing recorded, nothing provable — the current state of every row in that table.
