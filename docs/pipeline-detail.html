The pipeline

Power on, build, source

once per session

Pi boots, swap is mounted, then the workspace is sourced. colcon build --symlink-install compiles four packages we own; rf2o is cloned from deps.repos and pinned at b38c68e, so the build is reproducible rather than "whatever was on the SD card".

Fails as: a parallel build with no swap takes the machine off SSH — happened; build one job at a time.

Launch the graph

base.launch.py

Seven nodes start at once: robot_state_publisher (URDF → tf_static), the lidar driver, rf2o, imu_node, the EKF, motor_node and foxglove_bridge. The launch file forces dry_run: true, so motors compute duty cycles and log them but never touch a GPIO pin.

Fails as: /dev/rplidar missing → driver exits and the whole graph has no /scan; a stale bridge left on 8765 blocks the new one.

Lidar: one revolution, one scan

5–7 Hz

The A1M8 spins and streams range packets at 115200 baud; the driver assembles them into LaserScan on /scan with frame_id: laser and angle compensation on. Each revolution asks ~284 times; on this unit only 95–105 answers come back.

rplidar_rosconfig: serial_port, scan_mode/scan
Fails as: the 33 % missing-return rate — a photonic or mounting problem, not a driver bug. Every stage below inherits it.

IMU: yaw rate only

100 Hz

MPU6050 over I²C at 0x68. Three seconds of still bias calibration, then gyro z in rad/s on /imu/data. There is no magnetometer, so absolute heading is impossible — the node sets orientation_covariance[0] = -1 to tell every consumer the orientation field is invalid.

drivers.yamlcalib_max_std 0.01/imu/data
Fails as: i2cdetect -y 1 is currently empty — no 0x68 on the bus, so this stage has provably never produced a sample. Also needs robot in the i2c group.

Lidar odometry: range flow

10 Hz

rf2o compares consecutive scans and solves for the motion that best explains the change in ranges. It publishes velocity (vx, vyaw), not a pose — which is why a drift-prone position is never trusted downstream.

/scan → /odom_rf2opublish_tf: falsebase_frame_id: base_footprint
Fails as: with a third of the ranges missing, the flow field is thin in some sectors and the solution gets noisy exactly where the room is open.

Fusion: one owner of the odometry frame

30 Hz

robot_localization in 2D mode predicts forward at 30 Hz and corrects with rf2o's vx/vyaw plus the IMU's vyaw. It is the only publisher of odom → base_footprint. No accelerometer, no absolute position: x/y are integrals, so drift is bounded only by how good the velocity estimates are.

ekf.yamltwo_d_modeworld_frame: odom/odometry/filtered
Fails as: a second publisher of odom → base_footprint makes the map rotate on the spot — which looks exactly like broken hardware.

Map, or remember the map

per scan

slam_toolbox matches each scan against what it already knows and publishes map → odom plus /map. In mapping mode it grows a new map, which you save as maps/room.yaml plus a serialised pose graph. In navigation mode it loads that graph and only updates the correction.

slam_mapping.yamlslam_localization.yamlmaps/
Fails as: sparse scans produce walls that wobble; an unclosed loop makes the map jump when the robot returns to the start.

Decide where to go

on goal

A goal arrives in the map frame — from goals.yaml via deliver, or from a click in Foxglove. Nav2's planner finds a path over the costmap, and the controller follows it at 0.15 m/s, publishing /cmd_vel as TwistStamped (Jazzy stamps everything).

nav2_params.yamlgoals.yaml/cmd_vel
Fails as: an unstamped Twist is silently ignored — the robot looks dead while every topic appears healthy.

Turn velocity into volts

20 Hz

motor_node splits vx/vyaw into left and right wheel speeds, applies a dead zone and a gain per side, clamps at max_duty 0.85, and drives L298N on GPIO 12/5/6/13/20/21. If no command arrives for 0.5 s it zeroes PWM and pulls the direction pins low.

drivers.yamldry_runwatchdog_s 0.5
Fails as: teleop and Nav2 both publish /cmd_vel with no arbiter — there is no safety node yet, so the watchdog is the only protection.

The lidar is the slowest link by an order of magnitude, so the whole pipeline's reaction time is set by it: roughly 350 ms from a wall appearing to a PWM change — about 5 cm of travel at 0.15 m/s.

Where it breaks, in the order it will

Already broken

  • No IMU data — I²C bus scans empty; imu_node has never published.
  • No code — the repo is a skeleton; every node raises NotImplementedError.
  • No measurements — test_log.md rows are all blank.

Structurally fragile

  • Lidar dropouts feed odometry, mapping and localisation at once.
  • No safety node — two publishers on /cmd_vel, one actuator.
  • No absolute reference — yaw comes from integration, so drift never self-corrects.
